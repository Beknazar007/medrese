# Аудит репозитория «Медресе»

Дата: 9 ноября 2026. Ветка: `agents-setup` (от `main`, коммит 195ce75). Код не менялся.

**Итог.** Приложение небольшое (≈3,4 тыс. строк бэкенда, ≈4,3 тыс. строк фронтенда), аккуратно разделено на слои, все 88 адресов API кроме входа требуют авторизации, SQL-инъекций нет, секретов в репозитории и в истории git нет, 77 тестов бэкенда проходят. Перед переездом на свой сервер не хватает трёх вещей: образа Docker для бэкенда, резервных копий базы и защиты от запуска с секретом по умолчанию. Из уязвимостей серьёзнее всего библиотека JWT `python-jose` без исправленной версии.

## 1. Стек и запуск

| Часть | Технологии | Версии |
|---|---|---|
| Бэкенд | Python, FastAPI, SQLAlchemy 2 (ORM), Alembic, Pydantic 2, Uvicorn | Python ≥3.11 (CI — 3.13, локально — 3.11.1); FastAPI 0.128, SQLAlchemy 2.0.36, Alembic 1.18, Pydantic 2.12 |
| Авторизация | JWT (`python-jose`), пароли bcrypt через `passlib` | python-jose 3.5.0, passlib 1.7.4, bcrypt закреплён `==4.0.1` |
| Отчёты | `openpyxl` (недельный Excel) | 3.1.5 |
| БД | PostgreSQL (прод — Neon), драйвер psycopg 3 | локально `postgres:16-alpine`; тесты — SQLite в памяти |
| Фронтенд | React 19, TypeScript 6, Vite 8, MUI 9, TanStack Query 5, React Router 7, i18next (ky/ru/en), PWA (`vite-plugin-pwa`) | Node 22 в CI, локально 20.19 |
| Линтер | oxlint | 1.81 |
| Хостинг сейчас | бэкенд — Render (бесплатный тариф, США/Орегон), фронтенд — Cloudflare Pages, БД — Neon | |

**Как запускается (локально):**

```bash
docker compose up -d db                  # только Postgres
cd backend && pip install -e ".[dev]"
alembic upgrade head
python -m app.seed                       # первый аккаунт ректора из SEED_RECTOR_*
uvicorn app.main:app --reload --port 8000
cd ../frontend && npm install && npm run dev   # http://localhost:5173
```

**Тесты и проверки:** `cd backend && pytest -q` (77 тестов), `cd frontend && npm run lint && npm run build`.

**Прод:** пуш в `main` → GitHub Actions (тесты, линт, сборка) → Cloudflare Pages для сайта; Render сам собирает бэкенд после зелёного CI и в стартовой команде делает `alembic upgrade head`. Стартовая команда Render живёт только в настройках Render, в репозитории её нет.

**Конфигурация:** `.env` в корне (читается бэкендом как `../.env`), образец — `.env.example`; фронтенду нужен `VITE_API_BASE_URL` (`frontend/.env.example`).

## 2. Зависимости: устаревшие и уязвимые

### Бэкенд

Проверка `pip-audit` по зависимостям из `pyproject.toml` в чистом окружении (так ставит прод):

| Пакет | Проблема | Исправление |
|---|---|---|
| `python-jose` 3.5.0 | PYSEC-2026-4298; библиотека почти не поддерживается | исправленной версии нет → заменить на `PyJWT` |
| `ecdsa` 0.19.2 (тянет python-jose) | PYSEC-2026-1325 | исправленной версии нет → уйдёт вместе с python-jose |
| `passlib` 1.7.4 | не обновлялся с 2020 г., ломается с bcrypt ≥4.1 — поэтому bcrypt закреплён на 4.0.1 | использовать `bcrypt` напрямую |

Другие замечания:

- **Нет файла блокировки версий.** В `pyproject.toml` только нижние границы (`fastapi>=0.115`), поэтому каждая сборка на сервере ставит самые свежие версии. Сборка вчера и сегодня может дать разный результат.
- Локальное окружение разработчика расходится с декларацией: установлен bcrypt 4.2.1 при `bcrypt==4.0.1` в `pyproject.toml`. В нём же `cryptography` 48.0.0 с известными уязвимостями (исправлено в 48.0.1+). На прод это не влияет, но тесты локально идут не на тех версиях, что в проде.
- В репозиторий закоммичена папка `backend/medrese_backend.egg-info/`. Это артефакт сборки.

### Фронтенд

`npm audit`: 11 уязвимостей — 3 высоких, 5 средних, 3 низких. Все в инструментах сборки, не в коде, который попадает в браузер:

| Пакет | Уровень | Как исправить |
|---|---|---|
| `vite` 8.2.2 | высокий | обновить до 8.3.7 (в пределах `^8.2.2`) |
| `follow-redirects`, `source-map-js` | высокий | транзитивные, `npm audit fix` |
| `vite-plugin-pwa` 1.3.0 → `workbox-build`, `glob`, `minimatch`, `fast-uri` | средний | `vite-plugin-pwa` 2.0.0 (мажорное обновление, проверить сборку PWA) |
| `serialize-javascript`, `deepmerge`, `@rollup/plugin-node-resolve` | низкий | транзитивные, через `vite-plugin-pwa` |

Устаревшие в пределах текущих мажорных версий (безопасно обновить): MUI 9.4 → 9.5, React 19.2.8 → 19.3.1, TanStack Query, axios 1.20 → 1.21, i18next, react-router-dom, oxlint. Мажорные обновления, которые пока не нужны: TypeScript 7, `@types/node` 26.

### CI

`actions/checkout@v4` и `actions/setup-node@v4` выдают предупреждение о прекращении поддержки Node 20 на раннерах GitHub. ubuntu-latest с 19 октября 2026 переходит на Ubuntu 26.

## 3. Архитектура

```
backend/app/
  api/v1/      19 роутеров (по сущности на файл), router.py собирает их под /api/v1
  core/        config (pydantic-settings), deps (текущий пользователь, проверка ролей и кафедры), security (JWT, bcrypt)
  models/      модели SQLAlchemy (18 файлов)
  schemas/     Pydantic-схемы запросов и ответов
  services/    бизнес-логика: journal, hifz, excuses, monitoring, reports, workload, schedule_conflict
  seed.py      создание первого ректора
backend/alembic/versions/   12 миграций
backend/tests/              9 файлов, 77 тестов (pytest, SQLite, factories.py)
frontend/src/
  api/         axios-клиент, entities.ts (все вызовы API), types.ts
  pages/       17 страниц (вместе с teacher/), components/ (+ hifz/), context/, hooks/, lib/, i18n/locales (ky, ru, en)
```

**Что сделано хорошо:**

- Тонкие роутеры, логика вынесена в `services/`.
- Проверка прав в одном месте (`core/deps.py`: `require_role`, `assert_department_access`, `accessible_department_ids`).
- Уникальные ограничения в БД защищают от двойной записи: посещаемость, оценки, хифз за день, двойное бронирование расписания.
- Общий компонент `EntityCrudPage` для справочников.
- Мёртвых компонентов во фронтенде нет: каждый файл в `components/`, `lib/`, `hooks/` где-то импортируется.

### Слабые места

**Безопасность**

| # | Где | Проблема |
|---|---|---|
| S1 | `core/config.py` | Если `JWT_SECRET_KEY` не задан, сервер молча берёт `"change-me-to-a-random-secret"`. На новом сервере достаточно забыть переменную, и любой сможет подделать токен ректора. |
| S2 | `api/v1/auth.py` `/login` | Нет ограничения попыток входа: пароли можно перебирать без задержек. |
| S3 | `schemas/auth.py`, `user.py`, `teacher.py` | Нет минимальной длины пароля: можно поставить пароль `1` или пустой. |
| S4 | `core/security.py` | Токен живёт 8 часов и не отзывается: после смены пароля или удаления учителя старый токен действует до истечения. |
| S5 | `frontend/src/api/client.ts` | Токен хранится в `localStorage`: при XSS его можно украсть. Пока XSS-векторов не найдено, React экранирует вывод. |
| S6 | `schemas/student.py` | Фото ученика — base64 в колонке `Text` без ограничения размера на сервере. Один запрос может записать мегабайты в БД. |
| S7 | `docker-compose.yml` | Пароль БД `medrese/medrese` прямо в файле, порт 5432 открыт наружу. Для локальной разработки нормально, для сервера — нет. |
| S8 | — | Ключи Render, Cloudflare, Neon и JWT-секрет передавались в переписке с ассистентом. В репозитории их нет, но для надёжности их стоит сменить при переезде. |

SQL-инъекций нет: все запросы идут через ORM и выражения SQLAlchemy, сырого SQL и f-строк с SQL нет. Секретов в отслеживаемых файлах и в истории git не найдено (поиск по шаблонам ключей Render, Cloudflare, Neon и JWT).

**Права доступа (проверено по коду всех 88 адресов):** вход открыт, остальные требуют токен. Запись в справочники разрешена только RECTOR/DEAN, а в семестры, кабинеты, звонки и аккаунты — только RECTOR. Журналы может писать только TEACHER и только по своим урокам. Декан видит только свою кафедру. Сквозная проверка 82 сценариев (9 ноября) это подтвердила. Пробел: учётную запись нельзя отключить (`is_active` есть в модели, но API его не меняет), только удалить учителя целиком.

**Производительность** (замер количества SQL-запросов на тестовой базе с 42 учителями и 306 учениками):

| Адрес | SQL-запросов | Замечание |
|---|---|---|
| `GET /teachers` | 44 на 42 учителя | N+1: отдельный запрос на каждого учителя (ленивая загрузка `user`). Ни одного `selectinload`/`joinedload` в коде при 44 связях в моделях |
| `/students`, `/dashboard/workload`, `/excuses`, `/users` | 2 | в норме |
| `/monitoring/teachers`, `/hifz/journal` | 5–9 | в норме, не растёт с числом записей |

- **Нет индексов** на внешних ключах, по которым идут выборки: `attendance_records.student_id` (история ученика), `grades.student_id`, `student_notes.student_id`, `lesson_sessions.date` (мониторинг по датам), `hifz_exams.student_id`, `hifz_targets.student_id`, `schedule_entries.teacher_id`/`group_id`. На одном медресе незаметно, при общей базе на много медресе станет медленно.
- `GET /students` отдаёт фото всех учеников списком. Сейчас фото ни у кого нет, и ответ весит 189 КБ на 409 учеников. Но с фото по 30–50 КБ это 12–20 МБ на каждое открытие списка.
- Бесплатный тариф Render засыпает без запросов: первое открытие утром ждёт до минуты. Во фронтенде на это уже есть `SlowServerNotice`.

**Дублирование и мёртвый код**

- `todayIso()` определена четыре раза: `hifzUtils.ts`, `lib/dateRanges.ts`, `HifzJournalPage.tsx`, `TeacherClassPage.tsx`. В `TeacherClassPage` она берёт дату по UTC: с 00:00 до 06:00 по Бишкеку журнал откроется на вчерашнюю дату. В хафиз-журнале это уже исправлено.
- Таблица цветов посещаемости `ATTENDANCE_COLOR` объявлена отдельно в `AttendanceToggle.tsx` и `StudentProfileDialog.tsx`, `BISHKEK_TZ` — в `services/journal.py` и `services/monitoring.py`.
- Мёртвые файлы: `backend/medrese_backend.egg-info/`, `frontend/src/assets/hero.png`, `react.svg`, `vite.svg` (нигде не используются), `frontend/README.md` — шаблон Vite.
- Жёстко зашито: название института (`app_title` в i18n, `title` FastAPI), часовой пояс `Asia/Bishkek`. Для сети медресе это должно стать настройкой.

**Наблюдаемость:** журнал изменений хифза пишется только в лог Uvicorn (`audit_log` в `api/v1/hifz.py`), а логи бесплатного Render хранятся недолго. Сбора ошибок (Sentry и т.п.) нет. `/health` не проверяет соединение с БД.

## 5. Роли и сценарии

В системе три роли (`UserRole`): **RECTOR**, **DEAN**, **TEACHER**. Хафиз-учитель — это TEACHER, у которого есть группа типа `HAFIZ`. Для него открывается хафиз-журнал вместо обычного.

### Ректор (RECTOR) — всё медресе

- **Главная:** нагрузка учителей, предметы без учителя, сводка мониторинга и посещаемости, выбор семестра.
- **Справочники:** отделения, предметы, группы, кабинеты, звонки, семестры (один активный).
- **Люди:** учителя (создание вместе с аккаунтом, смена пароля), ученики (с фото и историей), аккаунты деканов и администраторов.
- **Учебный процесс:** назначения «учитель — предмет — группа», сетка расписания с проверкой двойной брони, освобождения учеников (ставят «по уважительной» на уроки).
- **Контроль:** мониторинг учителей (план / проведено / пропущено / опоздания по датам), хафиз-журнал всех групп (только просмотр), недельный Excel-отчёт.

### Декан (DEAN) — своё отделение

То же, что ректор, но только в своём отделении. Не может: создавать и удалять отделения, управлять семестрами, кабинетами и звонками, создавать аккаунты.

### Учитель (TEACHER)

- **Расписание:** свои уроки на неделю.
- **Журнал класса (`/my-class`):** во время урока по расписанию открыть урок (фиксируется время прихода), отметить посещаемость, при уроке-экзамене поставить оценки, завершить урок (время ухода). Сохраняется само. Прошлый урок задним числом открыть нельзя.
- **Заметки об ученике:** личные или видимые руководству; карточка ученика.
- **Итоги класса:** средний балл и посещаемость по своей группе.

### Хафиз-учитель (TEACHER с группой HAFIZ)

- **Хафиз-журнал, вкладка «Урок»:** открыть урок, посещаемость, оценки хифза и такрара за день (джуз, страницы, комментарий).
- **Вкладка «Журнал»:** таблица оценок за период, автосохранение каждой клетки; экзамены ученика (название, дата, джузы, балл).
- **Вкладка «Задания»:** цели на период для одного ученика или группы, прогресс по оценкам.

## 6. Что исправить перед переездом на новый сервер

### Критично (без этого не переезжать)

1. **Образ Docker для бэкенда** и `docker-compose` для сервера: бэкенд + Postgres + HTTPS-прокси, БД без внешнего порта, пароли только из `.env`.
2. **Отказ стартовать с секретом по умолчанию.** Если `JWT_SECRET_KEY` пуст или равен значению из `.env.example`, сервер не должен запускаться (S1).
3. **Резервные копии:** ежедневный `pg_dump` вне сервера и проверка восстановления. Перенос данных Neon → новый Postgres через `pg_dump`/`pg_restore` с проверкой количества строк по таблицам.
4. **Смена всех ключей** при переезде: JWT-секрет, пароль БД, токены Render и Cloudflare (S8). Смена JWT-секрета разлогинит всех пользователей; предупредить заранее.
5. **Закрепить версии зависимостей бэкенда** (lock-файл или `requirements.txt` с точными версиями), чтобы на сервере собиралось ровно то, что прошло тесты.

### Важно (в первые недели после переезда)

6. Заменить `python-jose` на `PyJWT`, `passlib` — на прямой `bcrypt`; снять закрепление `bcrypt==4.0.1`.
7. Ограничить попытки входа (S2) и ввести минимальную длину пароля (S3).
8. Ограничить размер фото на сервере и убрать фото из ответа списка учеников (S6).
9. `npm audit fix` и Vite 8.3.7; затем отдельно `vite-plugin-pwa` 2.
10. Индексы на внешних ключах из раздела «Производительность» (миграция Alembic) и `selectinload` в `GET /teachers`.
11. `/health` с проверкой БД, сбор ошибок, хранение логов; аудит изменений хифза в таблицу, а не только в лог.
12. Отключение аккаунта (`is_active`) вместо удаления учителя.
13. Прогонять тесты бэкенда и на Postgres (в CI — сервис postgres), а не только на SQLite.

### Желательно

14. Удалить мёртвые файлы (`egg-info`, неиспользуемые картинки, шаблонный `frontend/README.md`).
15. Одна функция `todayIso` по местной дате (исправит дату журнала после полуночи), одна таблица цветов посещаемости, один `BISHKEK_TZ`.
16. Название медресе и часовой пояс — в настройки (задел для сети медресе).
17. E2E-тесты Playwright по ролям; добавить их в CI.
18. Отзыв токенов при смене пароля (версия токена в пользователе); подумать о cookie `httpOnly` вместо `localStorage`.
